# Design: knowledge-review-mvp

## Context

全新项目，`openspec/specs/` 下无既有能力。动机见 `proposal.md`，需求见 `specs/`。

约束条件（决定了下面每一个决策）：

- **单用户个人工具**，无并发、无多租户需求
- **一台公网可达的云服务器**，带持久磁盘
- **飞书企业自建应用**：长连接收消息无需公网 IP，但 Web 界面需被手机访问，故仍需公网地址
- **DeepSeek API**，且只能在 18:00–09:00 调用
- **技术惯例由姊妹项目确立**：`2026-10/01-学习向导项目/hys-tutor` 使用 Vue 3.5 + Vite + TypeScript + Pinia + vue-router + Vitest + zod，并以 `node --env-file=.env` 原生加载环境变量。本项目沿用同一套，不另起炉灶。

## Goals / Non-Goals

**Goals:**

- 单个 Node 进程承载全部后端职责：飞书长连接、待处理队列、复习调度、定时提醒、Web API、前端静态托管
- 数据以人类可读的 JSON 落盘，可直接备份、直接进版本库
- 密钥零入库，且这条约束由工具链（`.gitignore` + 提交前扫描）保证而非靠自觉
- 部署与回滚都简单到一个人能维护

**Non-Goals:**

- 水平扩展、高可用、多实例
- 高并发与低延迟优化
- 引入数据库或消息队列中间件
- 离线可用、原生 App、多用户

## Decisions

### D1. 单进程 Node 服务，不拆分

飞书长连接是进程内的长生命周期连接，HTTP 服务与它同进程最简；单用户流量下拆分的唯一效果是增加运维面。由 pm2 托管，崩溃自动重启，数据在磁盘上，重启不丢。

*备选*：worker / API 分离 —— 无收益，否决。

### D2. 飞书长连接（WebSocket）接收事件，而非 Webhook

长连接免去公网 IP、域名、ICP 备案与 TLS 证书的整套配置，官方 SDK 已处理通信加密与鉴权。

**关键代价**：飞书要求事件在 **3 秒内**处理完毕且不抛异常，否则触发重推。这直接塑造了 D4。

*备选*：Webhook —— 国内节点需域名备案，MVP 阶段收益为负。

*已知限制*：长连接为集群模式、**不广播**，同一应用多客户端时只有随机一个收到事件。MVP 保持单实例即可；将来若多实例，需引入去重。

### D3. JSON 文件存储，而非数据库

单选用户、数据量小（预估数百至数千张卡片）的前提下，JSON 的收益是：无运维面、人类可读、可直接备份、可直接进 git 看历史。

代价是缺少并发写保护、查询能力与事务。缓解方式：**单写者模型** —— 所有写操作经单一进程串行化，写入采用「写临时文件 + 原子重命名」，避免进程中途被杀导致半写文件。

*备选*：SQLite —— 技术上是更适合的选择（事务、查询、单文件），但用户明确要求 JSON。

*退出条件*：卡片量级破万、或引入多用户时，迁移到 SQLite。正因如此，业务代码不直接操作文件，而是经一层薄存储接口。

### D4. 队列解耦，收到即回执

D2 的 3 秒限制与「大模型只能夜间调用」叠加后，同步处理不可行 —— 白天收到的知识不可能在 3 秒内处理完。

形态：**收到消息 → 立即回执并结束事件处理 → 交由队列**。队列落盘，进程重启不丢条目。

*备选*：收到后异步后台处理并立即回执 —— 仍然会在白天调用大模型，违反时段约束，否决。

### D5. 大模型调用窗口 18:00–09:00（跨午夜）

用户要求，且该窗口正好完整避开 DeepSeek 的高峰时段（工作日 09:00–12:00、14:00–18:00），落入五折区间。

**实现陷阱**：这是跨午夜窗口，判定式必须是 `hour >= 18 || hour < 9`。写成 `18 <= hour && hour < 9` 会得到一个永远为假的条件，且不会报错 —— 表现为"功能静默不工作"。窗口边界应作为独立可测单元。

*备选*：不设窗口 —— 违反用户要求且成本翻倍，否决。

### D6. 固定间隔表 + 二值反馈，而非 SM-2 / FSRS

间隔表 `[1, 2, 4, 7, 15, 30]`（天），卡片阶段 0–5。标记「记住了」则阶段 +1 并按新阶段取间隔；标记「没记住」则阶段归零、次日再来；阶段 5 再成功即标记为已掌握、移出复习队列。

选择二值而非多级评分，是因为"记住了 / 没记住"是让间隔表能**推进**的最小反馈。没有它，纯定时曲线会导致被划过去的卡片反而推进得更远 —— 而恰恰是你不熟的卡片最容易被划过去。

*备选*：SM-2（需 ease 因子与多级评分）、FSRS（需参数拟合）—— MVP 阶段过度，且用户明确表示间隔不是当前重点。

### D7. 数据模型为升级预留

卡片字段：`id / question / answer / stage / nextReview / history / mastered`。

升级到 SM-2 只需增加 `ease` 字段并扩展 `history` 的记录结构，不必重做数据。这是把 D6 的"简单"与将来的"更好"隔离开的关键。

### D8. 前端 Vue 3 + Vite + TypeScript

与姊妹项目 `hys-tutor` 的技术惯例一致，避免同一台机器上出现两套前端范式。构建产物为静态文件，由同一个 Node 进程托管，不额外起前端服务。

*备选*：无构建步骤的原生页面 —— 对两个页面够用，但既然确定要做成会长期生长的应用，且用户已选定 Vite，则从组件化起步。

### D9. 访问控制：单口令

公网 URL 必然被扫描器扫到，而库中存放的是个人全部知识。单口令 + 签名 cookie 的成本极低。

形态：口令经 `.env` 注入（不硬编码）；校验通过后下发 `HttpOnly` + `Secure` + `SameSite` 的签名 cookie；中间件统一拦截，未通过者拿不到任何内容。

*备选*：飞书 OAuth —— 更正规，但对单用户 MVP 过重，且引入对飞书可用性的额外依赖。

### D10. 密钥管理

全部密钥经 `.env` 注入，用 `node --env-file=.env` 原生加载（与姊妹项目一致，无需 dotenv 依赖）。`.env` 列入 `.gitignore`，且每次提交前扫描硬编码密钥 —— 这条规则已写入 `AGENTS.md`。

### D11. 时区显式化

提醒时刻（07:30 / 18:30 / 21:00）与大模型调用窗口均按东八区计算，与服务器系统时区解耦，避免服务器默认 UTC 导致提醒错位。

## Risks / Trade-offs

- **[JSON 文件并发写损坏]** → 单写者串行化 + 写临时文件后原子重命名；业务代码经存储接口而非直接操作文件
- **[飞书 3 秒事件超时导致重推]** → 回执先于处理发出，处理一律入队
- **[长连接集群不广播，多实例时丢事件]** → MVP 保持单实例部署；代码中记明此约束
- **[公网暴露个人知识库]** → 单口令 + HTTPS + HttpOnly cookie；口令需满足最低强度
- **[DeepSeek 偶发不可用或返回非法 JSON]** → 失败条目保留在队列，下个时段重试；不写入半成品课程
- **[密钥误提交]** → `.gitignore` 先行建立（已在首次提交前完成）+ 每次提交前扫描
- **[单进程即单点]** → pm2 自动重启兜底；状态全在磁盘，重启不丢数据
- **[跨午夜窗口判定写错且静默]** → 窗口判定抽为独立纯函数并配单元测试覆盖边界（17:59 / 18:00 / 08:59 / 09:00）
- **[提醒重复打扰]** → 当日已完成即抑制；0 张时只告知一次；推送失败不标记为已告知

## Migration Plan

全新项目，无数据迁移。

首次部署顺序：服务器安装 Node → 拉取仓库 → 写 `.env`（飞书凭据、DeepSeek Key、访问口令）→ `npm ci && npm run build` → `pm2 start`。

回滚：代码回滚不影响数据 —— JSON 是独立文件，且部署前备份 `/data` 目录即可。

## Open Questions

- **HTTPS 终止方式**：由 Caddy / Nginx 反代自动签发证书，还是直接在 Node 内终止（如自签）。不影响代码结构，可在部署阶段决定
- **口令凭证的有效期长度**：先取值"长期有效、可手动撤销"，若体验不佳再引入过期策略。不影响数据模型与任务拆分
